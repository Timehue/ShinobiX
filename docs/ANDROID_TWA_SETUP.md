# Android TWA setup (Google Play)

The Android app is a **Trusted Web Activity** — a thin Play-distributed shell
that opens `https://shinobijourney.com` in the user's Chrome. There is no second
codebase and no forked build: the shell renders the same live site, so a Railway
deploy updates the Android app with no Play review.

TWA rather than Capacitor for one decisive reason: `lib/google-signin.ts` uses a
top-level redirect, and TWA runs in Custom Tabs — real Chrome — so Google OAuth
works untouched. A Capacitor WebView is an embedded user agent, which Google's
sign-in servers reject with `disallowed_useragent`.

## What is already in this repo

| Piece | Where |
| --- | --- |
| Web app manifest | `shinobij.client/public/manifest.webmanifest` |
| Launcher icons (192, 512, maskable 512, apple-touch) | `shinobij.client/public/icon-*.png`, generated by `scripts/gen-pwa-icons.mjs` |
| Manifest + apple-touch links | `shinobij.client/index.html` |
| Digital Asset Links endpoint | `server.ts`, `/.well-known/assetlinks.json` |

Regenerate icons after any `favicon.svg` change:

```bash
node scripts/gen-pwa-icons.mjs
```

## What is NOT in this repo

The Bubblewrap output — the generated Gradle/Android project and the signing
keystore. Keep the keystore **out of git**; losing it or leaking it are both
unrecoverable in different directions.

## First-time setup

1. **Create the Play Console account** ($25, one-time) and complete identity
   verification. Note the testing gate below before planning dates.

2. **Generate the Android project.** `applicationId` becomes your package name
   and can never change for the life of the listing:

   ```bash
   npx @bubblewrap/cli init --manifest https://shinobijourney.com/manifest.webmanifest
   ```

   Set `targetSdkVersion` to **36**. Since 2026-08-31 new submissions must target
   Android 16.

3. **Build the bundle:**

   ```bash
   npx @bubblewrap/cli build
   ```

4. **Upload the AAB** to a closed testing track. This is what mints the Play App
   Signing certificate.

5. **Copy the SHA-256 fingerprint** from Play Console → Setup → App integrity →
   App signing key certificate.

6. **Set the Railway env vars** and redeploy:

   ```
   ANDROID_APP_PACKAGE=com.shinobijourney.app
   ANDROID_APP_SHA256_FINGERPRINTS=AB:CD:EF:...
   ```

   Until both are set, `/.well-known/assetlinks.json` returns 404 by design —
   "not configured yet" rather than a valid statement authorising nothing.

7. **Verify** before believing it works:

   ```bash
   curl -s https://shinobijourney.com/.well-known/assetlinks.json
   ```

   It must return JSON. If it returns HTML, the route is being shadowed by the
   SPA fallback and verification will fail silently — the app still runs, it just
   shows a browser address bar forever.

## Gotchas that cost real time

- **List every fingerprint, not just one.** During closed testing the Play App
  Signing cert and your local upload/debug cert are different keys. The env var
  is comma-separated for exactly this reason; listing one leaves the other build
  unverified and address-barred.
- **Route order is load-bearing.** The assetlinks route is registered before
  `express.static` and the SPA catch-all in `server.ts`. Moving it below either
  breaks verification without any error.
- **Cloudflare must not transform it.** The file has to be served from the exact
  origin in `start_url`, over HTTPS, with no redirect. Pick apex or `www` and
  keep the manifest, the asset links, and the Bubblewrap config on the same one.
- **The 12-tester gate.** Personal developer accounts created after 2023-11-13
  need 12 testers opted in *continuously for 14 days* before you may apply for
  production access, and Google checks they actually used the app. Budget the
  calendar time; it is the long pole, not the build.
- **Testing-track reviews are private.** Ratings and reviews from closed and open
  testing never reach the public listing, so an open test is a safe place to
  find the Android-specific bugs before the store rating can be affected.

## Surface split (app vs website)

`shinobij.client/src/lib/surface.ts` resolves the surface once per tab from
Chrome's `android-app://` launch referrer and persists it, because that referrer
is only present on the launch navigation and does not survive a reload.

It exists to vary **UI affordances only**. Every screen, feature, asset and API
call is identical on both surfaces — one build, no fork. Today it gates exactly
one thing (the hardware back button); the storefront button will be the second.

Two rules that are easy to get wrong:

- ⛔ **Never gate anything security-sensitive on it.** It is derived client-side
  and therefore forgeable, and the server cannot tell the surfaces apart on its
  own — the User-Agent is identical. A Play purchase is trusted because its token
  validates against Google's API, never because a client claimed to be the app.
- ⛔ **Do not use `display-mode: standalone`** for this. It is true in a TWA *and*
  true for a PWA installed via Add to Home Screen. Now that the site ships a
  manifest, those users are real, and they would be handed app-only UI that
  cannot work. For purchases, gate on `canUsePlayBilling()` — a capability probe
  for the Digital Goods API, which is the thing that actually has to be present.

**Android back button** is implemented in `lib/app-history.ts`, Play-app only.
It pushes a history entry per screen and walks the stack back. On the web it
pushes nothing and installs no listener, exactly as before it existed.

Its two refusal rules exist for real reasons, so do not relax them casually:
back is **refused while a battle is unresolved** (Forfeit stays the only exit —
otherwise back-then-refresh becomes a flee route, which is the bug `lastScreen.v1`
was added to close), and it **falls back to the village** when the popped entry
is a battle/encounter screen that cannot be restored from the save alone.

## Still to do

- **Offline fallback.** `public/sw.js` deliberately never intercepts HTML, so a
  dead network currently shows a Chrome error page inside the app shell.
- **Play Billing.** The storefront moves in-app via the Digital Goods API +
  Payment Request API (supported in TWA on Chrome 101+). Server-side this needs
  one endpoint that verifies the purchase token against the Google Play Developer
  API and calls `applyEntitlementToSave` in `api/_subscription.ts` — that
  function and the perk caps in `api/_entitlements.ts` are already in place and
  provider-neutral, so nothing else has to move. Play's Real-time Developer
  Notifications handle renewal and cancellation; a webhook that authenticates
  over raw bytes will need a scoped `express.json({ verify })` parser reinstated
  in `server.ts` (see the note where the Patreon one used to be).
