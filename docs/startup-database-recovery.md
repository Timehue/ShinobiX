# Startup database recovery

Clan-boss boot initialization and home-territory seeding run immediately, then retry known transient storage/connectivity failures or incomplete/contended work. Each process keeps one flight per job. Attempts use separate five-minute distributed startup leases; the daily clan-boss job retains its existing twenty-hour cadence lease. A failed attempt exits its lease context before retrying. Existing NX boss creation, fail-closed settlement/territory locks, exact territory CAS and reward receipts remain authoritative.

There are at most sixteen attempts per job. Equal-jitter backoff starts at 2.5–5 seconds and caps at 30–60 seconds. Fifteen waits total 6.1–12.3 minutes, plus actual work time; this is not a wall-clock timeout. A lost release is bounded by lease expiry. Expiry still fences further protected operations; it never authorizes unlocked writes. Waiting timers are unreferenced and cancelled on shutdown; each admitted attempt is included in background drain. HTTP startup remains independent of recovery completion.

Clan-boss recovery verifies that the current week exists and all ended weeks are settled. Lease contention is incomplete, never a completion signal. The current week is recomputed on every attempt. Feature kill switches are rechecked before storage admission and inside the lease. Rewards, combat rules, boss timing and territory resource/owner behavior are unchanged. Spawn/result announcements retain their existing best-effort semantics: a boss commit followed by a lost acknowledgement can leave its spawn announcement absent. This change does not add storage fields or replay old announcements to repair that separate limitation.

Recognized failures include PostgreSQL connection/exhaustion codes, installed pg-pool connection/acquisition timeout messages and supported nested causes. [PostgREST connection-group errors](https://docs.postgrest.org/en/stable/references/errors.html#group-0-connection) PGRST000–003 receive bounded retries, including pool-acquisition timeout PGRST003 and the fallback adapter's code-erased pool-timeout message. PGRST000 can also mean an incorrect database URI, so that code alone cannot prove a temporary outage. Known authentication/schema/missing-RPC failures and unclassified errors terminate, with known permanent nested causes taking precedence. The existing lock-acquisition wrapper discards its cause: `LockContendedError` can hide a permanent configuration error, so that path receives bounded ambiguous retries. Guarded REST error forms are tested separately. Logs contain job name, attempt count and status, without raw error/connection data. `permanent-or-unclassified-failure` and `exhausted` require investigation; they do not certify recovery. A longer outage exhausts this finite startup window. After correcting availability/configuration, an operator can use the existing authorized initialization workflow or restart normally; retries do not create an admin endpoint or bypass a kill switch. The existing daily clan pass remains scheduled, but territory recovery has no new indefinite polling loop.

## Pool sizing and player capacity

Runtime sizing is unchanged: Railway defaults to fifteen clients per Node process, other hosts to five, with the existing bounded `PG_POOL_MAX` override. Fifteen means reusable database connections, not fifteen players. Players share those connections across short operations. Source configuration declares one Railway replica and a sixty-second deployment drain, so process overlap is possible. The actual override, shared-role client occupancy, provider topology and overlap at the observed startup errors have not been measured; they must not be inferred from defaults or the error alone. Smaller pools previously caused burst/acquisition starvation, so this patch does not alter configured pool concurrency or raise provider limits. Retry work and completion verification add bounded background queries; unchanged settings do not prove unchanged player tail latency.

No production capacity promise follows from this limit. Illustratively, fifteen continuously busy connections completing one operation every 50 ms yield 300 operations/second; at 200 ms, 75 operations/second. These are arithmetic examples, not game capacity measurements: player actions can require multiple operations, background work consumes capacity, and locking/cache/network/queueing affect latency. The existing 24-player soak fixture is not a production player-capacity measurement.

Before recommending a sizing change, establish sanitized process/replica and pool configuration, all clients sharing the provider role/database, deployment overlap, pool wait/timeout behavior, query duration and realistic player-action/background demand. Test any proposed change against practical throughput and tail latency without exhausting production. Local tests here use in-memory domain storage and the installed pg-pool with a transport double; they verify replay, queue bounds, timeouts and recovery, not real PostgreSQL throughput or player latency.
