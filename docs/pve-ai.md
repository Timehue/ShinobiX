# Standard-PvE enemy AI

**Status:** current, 2026-09-25. Replaces `docs/pve-ai-smarter-plan.md`, whose
premise (a browser-owned `Arena.tsx` reducer) no longer exists.

Standard PvE runs entirely on the server, on the Solo-PvE runtime
(`api/solo-pve/`). The browser only sends the player's action and replays the
events it gets back. Enemy decisions are made inside the player's own request,
after the player's action resolves, by the same engine that resolves every
action. There is no client AI and no client authority for PvE outcomes.

## Where an enemy turn is decided

1. A host builds a sealed session with `buildSoloPveAiEncounter`
   (`api/solo-pve/_ai-encounter.ts`). The enemy's kit, stats, mastery, authored
   rule program and turn policy are sealed onto `session.enemy.character`.
2. `POST /api/solo-pve/action` → `executeSoloPveAction`
   (`api/solo-pve/_action-service.ts`) takes the session lock, checks the
   version and move token, and calls `applySoloPveAction`
   (`api/solo-pve/_engine.ts`).
3. The player's action resolves; if the player's turn ended, the companion
   phase and then `runSoloPveAiUntilPlayer` run the enemy's whole turn.
4. `runSoloPveAiUntilPlayer` sends a session sealed with
   `aiTurnPolicy: 'standard-pve-v1'` to the standard-PvE planner
   (`runStandardPveEnemyTurn`); every other session runs the original loop,
   unchanged.
5. Every enemy action goes through `directAction` → `resolveDirectAction`, the
   same resolver a player's action uses (AP, cooldowns, range, resources,
   Elemental Seal, the difficulty guard's per-hit and per-turn caps, damage).
   The finished session, including the event history, is stored; settlement
   and reward claims read that stored terminal state, so nothing is re-derived
   from a seed.

## What an enemy decides from

- **Profiles.** `api/_ai-profile-catalog.ts` holds the catalog (71 profiles on
  2026-09-25, generated by `scripts/ai-profile-catalog-gen.mjs`). Each profile
  fixes a level, vitals, stats, armor, a jutsu kit (`jutsuIds`), a loadout
  (`loadoutId`) and an authored rule program (`rules`). A host picks a
  profile, or builds its own enemy for mission kits and story bosses, and
  `buildSoloPveAiEncounter` seals it onto the session.
- **Brackets.** `api/_pve-difficulty.ts`: `pveDifficultyBand` (the brackets
  below), `pveAiCompetence` (the counterplay thresholds), `pveAiMasteryForLevel`,
  the per-hit and per-turn guard (`pveEnemyHitCap`), and the easy-band
  readability rules (`pveEasyBandHoldsBurst`, `pveEasyBandAllowsLethal`). None
  of them changed.
- **Budget.** 100 AP a turn, or 60 when stunned (`api/solo-pve/_engine.ts`); at
  most `MAX_ACTIONS` (5) actions a turn. The original runner also ends its turn
  below 30 AP.
- **Inputs.** Only the stored session: both fighters' sealed state, statuses,
  positions, cooldowns and the round. No clock, no randomness and no client
  input reaches a decision.

The gate is `standardPvePlannerApplies` (`api/solo-pve/_ai-turn-policy.ts`):
the seal must be present, the kind must be one of the five standard kinds, the
session must carry no weekly-boss guard, and the enemy must not be an authored
mission kit. A session keeps the runner it was sealed with, so fights in flight
when this shipped keep the original runner.

## The bracket policy

Brackets are the existing difficulty bands (`api/_pve-difficulty.ts`), read
from the enemy's level. An admin `masterAi` profile plans at any level, as it
already uses the smart scorer at any level.

| Bracket | Levels | What the enemy does |
| --- | --- | --- |
| easy | 1–30 | The original priority order and the original turn end (stop below 30 AP). The only change: it never picks an action the resolver would refuse. Readable and limited, as tutorials need. |
| medium | 31–50 | The original priority order, but it keeps acting while any legal action remains, so leftover AP is spent (40 + 40 + a 20-AP Flicker). |
| hard | 51–90 | Plans two-action combinations: each of the six best first actions is scored by its own result or by its best legal follow-up, simulated on a copy through the real resolver. |
| peer | 91+ | The same planner. (The band itself already removes the damage guard at level 100.) |

**Decision order** (every bracket): competence-gated counterplay (clear,
cleanse and heal, at the existing thresholds) → the authored rule program →
the bracket policy. An authored rule with a specific intent (a scripted
round-1 opener, a basic attack, a heal, a move, end turn) is honoured when the
resolver would accept it, and skipped to the next rule when it would not. A
rule that asks for "the best jutsu" (`use_highest_power_jutsu`,
`use_best_legal_jutsu`) and the generic fallback are decided by the bracket
policy. Every catalog profile's program ends in an unconditional basic attack
(`validateServerAiRules` requires it).

**Evaluation** (`enemyTurnValue`) scores a simulated state for the planner
only. It never feeds combat: damage the player took (HP plus shield, as a
share of max HP), vitality the enemy kept (weighted up when it is hurt), status
swings (statuses start next round, so a debuff is valued for the rounds
ahead), a large bonus for a knockout, and a small penalty for ending out of
reach. Ties fall to a stable action key. There is no randomness.

## Guarantees

- **No numeric change.** AP costs, damage, tag percentages, cooldowns,
  durations, stats, mastery, the per-hit and per-turn difficulty caps, and
  rewards are untouched. A higher bracket gets a better chooser, never a
  stronger fighter.
- **Legal actions only.** Every candidate is checked with the resolver's own
  acceptance rules before it is simulated or executed. If the resolver still
  refuses one, the turn ends; a refused pick is never repeated.
- **Hard limits.** At most five actions per turn (the engine's `MAX_ACTIONS`),
  never more AP than the turn grants (100, or 60 when stunned), and an
  iteration guard.
- **Deterministic.** Same stored state, same decisions, same events.
- **Bounded cost.** Per decision at most six first actions and one follow-up
  pass each; simulations copy the session without its event history and log.
- **Rollback.** `DISABLE_PVE_AI_PLANNER=1` stops sealing new sessions and sends
  sealed sessions back to the original runner immediately.

### Simulation

`node --import tsx scripts/pve-ai-planner-sim.ts` plays the same 256 fights
twice: eight catalog profiles re-levelled to each bracket, against the mission
simulator's earned-budget player (two disciplines, two scripts), once per
runner. Nothing but the turn policy differs. Measured 2026-09-25 (Node 24.15,
Windows):

| level | runner | player wins | mean rounds | enemy AP / turn | enemy actions / turn | idle enemy turns | max actions | max AP | turn p95 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 15 | original | 17 / 32 | 5.50 | 88.8 | 2.16 | 0 | 3 | 100 | 2.77 ms |
| 15 | planner | 17 / 32 | 5.50 | 88.8 | 2.16 | 0 | 3 | 100 | 2.95 ms |
| 40 | original | 0 / 32 | 5.88 | 87.8 | 1.99 | 0 | 3 | 100 | 2.35 ms |
| 40 | planner | 0 / 32 | 5.88 | 87.8 | 1.99 | 0 | 3 | 100 | 2.49 ms |
| 70 | original | 0 / 32 | 7.44 | 86.8 | 1.96 | 0 | 3 | 100 | 2.38 ms |
| 70 | planner | 0 / 32 | 7.38 | 86.8 | 1.96 | 0 | 3 | 100 | 4.21 ms |
| 95 | original | 0 / 32 | 10.63 | 86.8 | 1.99 | 0 | 3 | 100 | 2.78 ms |
| 95 | planner | 0 / 32 | 10.59 | 88.3 | 2.02 | 0 | 3 | 100 | 4.62 ms |

Read this honestly: on today's catalog kits the milestone barely moves the
numbers. Easy and medium are identical (no sampled kit has a 20-AP option to
spend). Hard and peer finish fights marginally sooner. No balance target was
changed and none needs to be. Two facts of the resolver limit what
within-turn planning can add, and they are why the gains are small:

- A **40-AP cast deals no damage** unless its definition sets
  `isUtility: false` (`isZeroDamageFortyApJutsu`,
  `api/combat-core/formulas.ts`); every 40-AP starter jutsu is a two-tag
  utility. Damage comes from 60-AP casts and the 40-AP basic attack.
- **Statuses start next round** (`activeRound = round + 1`), so a debuff never
  amplifies a hit in the same turn.

The player script loses to most enemies above level 15 in this harness. That
is the harness's simple player, not a balance finding.

## Deferred, deliberately

- Retreat, kiting and ranged spacing: the planner's only move is the step
  toward the player, as before.
- Weapons and items for AI actors: enemies carry none, and giving them some is
  a balance change.
- Telegraphs and boss phases in Solo (they exist only on the tower engine).
- Deeper search (three or more actions) and companion-aware planning.
- `readsBehavior` (still inert) and any use of the player's action history
  beyond the authored `player_recent_action` condition.
- Adopting the planner in the protected Solo hosts. Each is a balance decision
  for its own mode.
- **Known defect left in the protected hosts:** the original runner still loses
  a whole turn when its best pick is refused (for example an Elemental-Sealed
  elemental jutsu). Fixing it there makes those modes harder when a player
  uses Elemental Seal, so it needs an owner ruling per mode.
