## Publish a revision

The authenticated game route `POST /api/avatar-model/equip` takes `{"assetId":"<id>"}`. Send `{"assetId":null}` to return to the default. The server checks the owner's ready asset metadata and derives the version from it. The save write and the ownership check share one transaction. The response returns the equipped reference and save version. A retry with the same selection leaves the version alone. Connected players receive the change through sector presence. Creation and publication must supply the verified asset record before a player can equip a new revision.

The local player worker keeps the audited three-style movement archive in the request's private checkpoint directory until it verifies the published game objects. A restarted delivery checks the portrait, fitted-master identity and archive checksum before encoding again. Explicit movement rebuilds from saved art take the normal render path. The checkpoint contains private artwork and stays outside the public content prefix.

If a completed local job loses browser files, rerun `render_admitted_sprite.py` on the same job directory with the original encoder available through `SHINOBIX_FFMPEG`. It verifies the private fitting and movement archive, reconstructs the recorded revision in a temporary directory, then atomically replaces damaged or missing files. It checks the full delivery before returning the equipment reference. A different encoder output stops recovery before it modifies the existing files.

For an NPC whose artwork has passed visual review, run `python scripts/import-sector-model.py --fitted-npc --reviewed-master <reviewed-fitting-sha256> <worker-result-folder> <slug> <bundled-portrait>`. Take the fitting digest from the reviewed master’s receipt. The importer checks it against the completed job and its fitted descriptor, verifies the portrait and each public object, then updates the local NPC pin. The private fitting and download archive stay in the worker folder. Run the staged model test and the sector NPC movement and talk test before promoting the revision.

Serve the files at `R2_PUBLIC_BASE/sector-models/<slug>/<hash>.<extension>`. Upload the WebP sheets before their manifest, and verify all objects before deploying a client that references the revision. Serve JSON as `application/json` and WebP as `image/webp`. Allow cross-origin GET for the game origin and send `Cache-Control: public, max-age=31536000, immutable` for hash-named objects. Keep prior revisions available to clients with older pins.

The server exposes the artwork URL and walk/run controls by default when the existing public art base is configured. An incident override of `ENABLE_SECTOR_MODEL_DISPLAY=0` restores the portrait display after the layout is refreshed.

### Run the private sprite worker locally

The Linux reproduction used CPython 3.12.14, separate painting and detector virtual environments, Blender 4.5.11 LTS, and the FFmpeg executable shipped by the pinned imageio-ffmpeg package. Exact package versions for both environments are under `workers/avatar-model/requirements-linux-*.txt`. The tested detector uses the CUDA 12.6 PyTorch wheels. To resolve the FFmpeg executable from the painting environment, run `python -c "import imageio_ffmpeg; print(imageio_ffmpeg.get_ffmpeg_exe())"`.

The private payloads pinned by `sprite-worker-release.json` are `portable-fit-worker/profile-intake.zip` and `portable-motion-worker/browser-motion.zip` under the avatar-model artifact directory.

Install the two private release archives once per worker image. Run the installer with Python 3.11 or later. Use the fitting environment for the artwork commands, the detector environment for the portrait read, and the installed Blender and FFmpeg executables for movement. Set `SHINOBIX_FFMPEG` to the FFmpeg executable if it is absent from PATH.

```text
python workers/avatar-model/install_sprite_worker.py <intake-zip> <movement-zip> <new-private-install-directory>
python <installed-entry-directory>/portrait_intake.py <private-portrait> <new-master-directory> --source-sha256 <expected-portrait-digest> --reader-python <detector-python>
python workers/avatar-model/render_admitted_sprite.py <installed-entry> <master-directory> <private-job-directory> --master-sha256 <fitted-master-digest> --blender <blender-executable>
```

The installer prints the installed entry path. The read writes `read.json`. A refusal ends the read. For an accepted result, the caller takes `fittedMasterSha256` from that receipt. Run the final command only for a job admitted by the game. Every retry of that job uses the same private directory. Completed styles are recoverable there. A completed job returns the same asset ID and version after rechecking its data. Logs go to standard error, and a successful result goes to standard output as JSON. The directory lock coordinates workers sharing that local filesystem. Hosted account admission, distributed ownership and moderation still need their own integration.

### Provider cost reconciliation

The dispatcher keeps the provider call ID for each acknowledged stage and attempt on the private job, including expired outputs and failed retries. Recognition also retains the Responses `responseId` and token usage on a completed verdict, including rejection or a cancellation that wins during the review. Reporting a final charge requires a trusted, job-specific, complete USD statement from billing records. A token count or an estimate is insufficient. An OpenAI statement must include the recorded recognition `responseId` on its corresponding charge line. Interrupted or refused responses remain in the private R2 execution journal for operator reconciliation. Unresolved submissions and incomplete billing records retain their reservation.

From the game server project with its storage environment selected, preview a normalized statement using `node --import tsx scripts/reconcile-avatar-cost.ts statement.json`. Supply `--apply` to post it. The private CLI reads a document shaped like the example below. Replace every example value with the actual job, asset and itemized billing data. A zero-cost line requires an explicit provider confirmation. Include every attempt and all provider billing cycles the job crossed.

```json
{
  "jobId": "example-job",
  "assetId": "0123456789abcdef0123456789abcdef",
  "provider": "modal",
  "currency": "USD",
  "final": true,
  "charges": [
    {"eventId": "example-usage-line", "callId": "fc-example", "cycle": "example-cycle", "micros": 12500}
  ]
}
```

Micros are millionths of one US dollar. A completed, failed or cancelled job may settle each provider separately. The transaction reserves no new spending. It releases the original reservation, posts actual costs to each billed cycle and claims the provider's usage line IDs together. The same statement can be replayed. Conflicting charges and shared line IDs require investigation. The local tests use fixture billing records. Automatic import from a live provider billing feed still needs qualification.

A normalized Modal charge can include the optional `billedMilliseconds` field when the billing record confirms the duration. Include it on every line to record a job's total worker time. A confirmed duration of zero is valid. Check the original statement before posting because the duration is part of its replay fingerprint.
