# First defeat and recovery audit — 2026-09-13

**Executive summary:** The validated local desktop/mobile journey is coherent after five focused corrections: one P0, three P1s, and one P2. The 18-scenario browser matrix and 258 focused checks pass. Defeat persists, recovery is admission-bound and retry-safe, and the player can resume another activity and log back in with consistent state. One existing, low-risk logout-throttle issue remains (DR-06).

## Phase 1 — findings recorded before production edits

Audited the existing working tree. Other passes already had uncommitted changes; this pass preserves those. No production code was changed before this ledger. The baseline uses the real Express server, authenticated disposable accounts, isolated in-memory storage, the current production client build, and Chromium at 1366×768 and touch-enabled 390×844. Account preparation and the exploration receipt are explicit admin test fixtures; combat actions, terminal evidence, settlement, recovery, and save reads use actual player endpoints. This is local runtime evidence, not a production-account or physical Android certification.

The initial exploratory fixture was normalized by the server to sector 51. Final journeys read the account's actual canonical sector and bind the prepared exploration receipt to that location. The server also normalizes this level-three fixture's maxima to 700 HP and 1,181 chakra/stamina; the final fixture supplies those maxima directly. Idle recovery before combat explains the difference between initial and immediately precombat vitals. Server encounters carry `continuousVitals: true`; no combat balance was altered to induce defeat. The player uses Wait and takes real enemy damage to zero HP.

### Changes made

- **DR-01:** `api/player/heal.ts` requires the reviewed `hospitalizedAt` stamp under the save lock. Same-stay retries return the existing discharge; a delayed prior-stay request returns 409 before debit or healing. Explicit zero preserves legacy unstamped saves. Current-client paid, free, and healer self-checkout send the stamp. Costs, discounts, exemptions, HP-only treatment, and cross-healer transactions retain their existing rules. [Before probe](first-defeat-recovery/before/delayed-recovery-probe.json) charged twice; [after probe](first-defeat-recovery/after/delayed-recovery-probe.json) retains 7,500 ryo and the newer admission.
- **DR-01:** Both checkout requests have a 12-second deadline. Ambiguous payment responses show inline retry guidance; replays say “Discharge confirmed” instead of calling the earlier purchase free. Feedback uses the server's charge.
- **DR-02:** `App.tsx` fetches and accepts the current versioned save before acknowledging a healer notice. It never manufactures healing from a notification. A later admission remains admitted; a healthy snapshot produces feedback and exits the hospital even when another accepted read cleared the local flag first.
- **DR-03:** `AiFightHost.tsx` uses the accepted consequence for result text and destination. A settled knockout names the HP loss, hospitalization, and absence of rewards, then offers Go to Hospital. Unconfirmed/failed settlement states say so. A surviving retreat reports remaining HP and retains Return.
- **DR-04:** The existing ward explains the travel/combat restriction, full-HP treatment, timer/price, village destination, and separate rest/Cafeteria recovery for chakra and stamina. Existing buttons, layout, art, and motion rules remain.
- **DR-05:** Achievement responses adopt their matching vitals and hospital stamps with achievements, wallet, and save version. Incomplete vital snapshots are rejected; unrelated local choices remain intact.

### Remaining known risks and launch verdict

- **DR-06, low risk:** the observed save-burst logout rejection retains the player session and offers Cancel. The regression uses safe retry instead of Log out anyway. No save/cost loss was observed. This pass does not alter the shared logout/save coordinator.
- **Compatibility:** a pre-update client missing the admission stamp must refresh before starting a new discharge. The 409 message explains this; legacy saves themselves remain supported.
- **Validation limits:** runtime work used isolated local Express/memory storage and Chromium, including the mobile Play surface. Physical Android/TWA lifecycle and production distributed storage/multiplayer require their release-device/environment checks; they are not represented as exercised here.

**PASS WITH KNOWN LOW-RISK ISSUES.** The validated journey explains the defeat, consequence, treatment, and next step, while preserving the existing game rules. No observed path can duplicate treatment charges, erase admission, resurrect an old defeat after recovery, or lose saved progress. DR-06 is temporary save friction with protection intact, and physical-device/production validation remains outside this local audit. No changes were deployed or committed by this pass.
