Build and retain fixed world-boss candidate and compatible recovery images, then load those same images into an isolated PostgreSQL qualification job. This is test tooling, not a production publisher. PR #42's release block remains independent.

The workflow runs manually or for same-repository PRs touching only its listed workflow/tooling paths. Fork PR jobs are skipped. Its token has contents read access, every checkout disables credential persistence, and there are no production secrets, registry pushes, Railway actions or deployment steps. Creating the draft PR can run this workflow before any merge.

`pins.json` fixes candidate b44446155a319be728a2c9bc80d8f3e117828ba5 and recovery 9851d8b25fce230ef48968f0678fe16d0a6977f4. Recovery retains all reviewed repairs and precedes only the test-fixture error-response follow-up. It is not an undo of the repairs. The tooling branch itself contains neither the repair nor a rollout mechanism. Future merged source needs its own explicit pin and qualification.

The retention job builds each role once from its SHA and exports an image archive. Identity records contain the source label, image/config ID, layers, archive/schema checksums, Dockerfile/lock hashes, platform, Node version and default configuration. The two immutable upload artifact IDs are passed to qualification, so rerunning only the failed qualification job consumes the successful producer artifacts rather than guessing the current run-attempt name. Rerunning retention creates new attempt-specific artifacts and preserves earlier attempts.

Qualification verifies the checksums and loaded identities before running either image. It checks the actual PID 1 command, executable, UID, Node version and health revision; requires the default compiled-server command; and mounts fixture controls read-only at `/qualification`, without replacing `/app`. PostgreSQL and the app use one internal Docker bridge; neither publishes a port. The Linux runner reaches HTTP directly at the inspected private bridge address, rejecting extra networks, public addresses and host-port requests. This follows [Docker's internal-network host access](https://docs.docker.com/reference/cli/docker/network/create/#network-internal-mode---internal) and avoids assuming a published-port entry exists on an internal-only network. The environment consists of synthetic test values. Application and PostgreSQL diagnostics, including network bindings, are saved before all generated containers/network are removed; synthetic session/database secrets are redacted from reports.

Database readiness requires an authenticated `SELECT 1` over container-local TCP in the intended database. The disposable cluster explicitly requires SCRAM host authentication, and a wrong-password query must fail with a password-authentication error before qualification proceeds. A socket-only readiness check can succeed against PostgreSQL's temporary initialization server before the database exists and before that server shuts down. Schema loading and session reconciliation use the same TCP connection settings. The first retained-image CI attempt exposed this startup race before any app or gameplay scenario ran; its failed diagnostics remain preserved.

Six scenario checks cover concurrent two-client joins and bounded 503 retries without duplicate tickets; known and unattributed periodic damage; exact stored expiry and move receipts across recovery; a database-triggered interruption after shared HP banking; resumed settlement; leaderboard credit; and once-only reward/save-version preservation across candidate/recovery transitions. Initial join statuses and retry counts remain in evidence. Fixture setup and trigger creation are guarded to a named disposable database; there is no public fixture endpoint.

The test disables scheduled jobs, snapshot cron, presence-state jobs and combat receipt background work through the existing flags. Socket initialization and territory startup initialization can still run. This is a bounded world-boss image test, not complete scheduling, presence, production-writer retirement or deployment certification. Containers stop and their PostgreSQL sessions must disappear before the next role starts.

These are NEW synthetic-build images. They do not recover the earlier ephemeral Production Image job, and are not claimed byte-identical to Railway's current source rebuild or public client build inputs. Image/config IDs, archive checksums and registry manifest digests are distinct; no registry digest is claimed. Artifacts last 14 days and must not be used as permanent rollback storage without a separate preservation decision. No merge or production promotion follows from a successful qualification job.

The host-only fixture rehearsal passed six checks on PostgreSQL 16.15 with Node 24.15.0 and one compiled local checkout serving both roles. That validates fixture logic only; actual retained images, separate recovery bytes and Node 24.21.0 still require this workflow's execution. Fourteen local configuration/integrity checks also pass. Full job success, artifact IDs and qualification output must be reviewed before making image claims.
